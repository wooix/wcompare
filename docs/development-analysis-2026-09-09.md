# wcompare 개발 내용 분석

분석일: 2026-09-09. 기준 커밋: `ef1b777`(2026-08-20). 패키지 버전 `0.1.0`, 빌드 표기 `2026-08-20-004`.

## 1. 제품의 현재 성격

wcompare는 **텍스트 파일 비교 도구로 출발해, 원문 PDF·한국어 번역·논문 요약·마크다운 메모를 함께 다루는 개인용 연구 독서 앱으로 발전**했다. 현재 앱의 기본 진입 모드도 PDF다.

텍스트에서는 Monaco가 실제 차이를 계산한다. PDF에서는 pdf.js가 두 문서를 나란히 보여 주고 스크롤과 탐색을 연결한다. **PDF의 변경점을 자동 계산하는 기능과 원문·번역본 대조 열람은 구별해야 한다.** 현재 구현의 중심은 후자다.

## 5. 기술 구조와 설계 평가

```text
사용자 입력·화면
  renderer/app.js
    ├─ Monaco 비교 편집기
    ├─ pdf.js 듀얼 뷰어·마커·탐색
    └─ 요약·메모·Markdown/KaTeX/Mermaid
            ↓ preload가 노출한 제한된 IPC
  main/ipc.js
    ├─ 허용 경로 검증·파일 입출력·설정·프로젝트
    ├─ 마커·요약 로컬 JSON 저장소
    └─ 외부 프로세스: transpaper / agy / claude / Ruff / ESLint
```

Electron 메인·preload·렌더러의 책임을 나누고, 파일 접근은 메인에서 검증한다. sandbox와 contextIsolation, `app://` 워커 로딩, CSP, DOMPurify를 사용한다. lint가 열린 프로젝트의 임의 설정 코드를 실행하지 않도록 격리 모드로 실행하는 것도 의도된 설계다. 다만 이것은 확인한 방어 장치의 설명이며 보안 감사 완료를 뜻하지 않는다.

핵심 엔진을 직접 만들지 않고 검증된 도구에 위임한 선택이 개발 속도와 기능 폭을 확보했다. 대신 Monaco 옵션의 상호작용, pdf.js의 렌더링·링크, GUI 환경의 PATH, 외부 LLM 프로세스 취소 등 **도구 사이의 연결이 주요 난제**가 되었다. 최근 커밋은 문제 원인과 잘못된 테스트 측정 방식까지 기록해 유지보수에 유용하다.

마커·요약·최근 목록은 임시 파일 후 rename으로 기록한다. 마커·요약 키는 문서 내용이 아닌 절대경로 기반 SHA-1이다. 따라서 파일 이동·사본·유니코드 경로 표현 차이를 자동으로 같은 문서로 취급하지 않는다. 여러 창에서 같은 문서의 데이터를 편집할 때도 병합 없이 마지막 저장이 이기는 구조다.

프레임워크 없이 JavaScript와 DOM으로 화면을 구성한다. 작은 모듈들은 단위 테스트하기 쉽지만 `renderer/app.js` 1,679줄, `main/ipc.js` 600줄에 여러 모드와 작업 상태가 모여 있다. 향후에는 PDF·요약·메모별 제어 로직을 분리하는 편이 변경 영향 범위를 줄인다.

## 6. 검증 결과와 확인된 문제

### 이번에 직접 실행한 검증

- `npm run build`: 성공.
- `npm test`: 423개 중 420개 통과, 3개 실패, 건너뜀 0개.
- 실패는 `test/defaultApp.test.js`의 `findDuti`, duti 미설치 시 조회, duti 미설치 시 지정 거부 케이스다. 격리된 PATH 대신 실제 `/opt/homebrew/bin/duti`가 발견되어 테스트 가정이 깨진다. 최신 커밋에 기록된 기존 실패와 일치한다.
- `summaryStore.sanitizeParts()`에 네 개 요약 필드를 넣었을 때 `narrative`만 빠지는 것을 직접 재현했다.
- E2E 전체, 실제 LLM 번역·요약, 패키징·설치본 육안 검증은 이번에 실행하지 않았다. 과거 커밋의 E2E 통과 기록을 현재 실행 결과로 간주하지 않았다.

### 우선 대응할 문제

| 우선순위 | 관찰한 문제 | 근거·영향 |
|---|---|---|
| 높음 | 핵심 정리(`narrative`) 캐시 누락 | 생성기·화면·내보내기는 네 개 탭을 지원하지만 `summaryStore.sanitizeParts()`는 세 개만 반환한다. 저장·복원 과정에서 핵심 정리가 빠진다. 함수 호출로 재현했다. |
| 높음 | 마커 저장 실패가 사용자에게 전달되지 않음 | `app.js` 일반 저장은 console.warn, pagehide 저장은 빈 catch다. 실제 저장 실패를 이번에 유발하지는 않았으나 실패 통로는 코드로 확인했다. |
| 중간 | 경로 동일성 규칙 불완전 | allowlist는 realpath, 최근 목록은 path.resolve, 저장소는 경로 해시다. Unicode NFC/NFD 통일이 없어 같은 문서의 키·최근 항목이 갈릴 가능성이 남는다. |
| 중간 | 번역본 재번역 가드 부재 | `pdf:translate` 출력 경로가 `.ko.pdf` 접미사를 추가하며 입력 번역본을 막는 가드가 없다. `.ko.ko.pdf` 생성 가능 경로가 남아 있다. 실제 LLM 호출은 하지 않았다. |
| 중간 | 단위 테스트 환경 의존 | 기본 앱 테스트 3건이 현재도 실패한다. 외부 바이너리 탐색 위치를 주입 가능하게 하여 환경을 격리할 필요가 있다. |
| 중간 | 문서와 코드의 차이 | README의 “프로젝트로 저장하지 않으면 마커 소실”, 요약 세 탭 설명은 현재 코드와 다르다. 과거 로드맵의 미구현 항목도 현행화해야 한다. |

핵심 정리 누락은 전체 단위 테스트의 기존 실패 3건과 별개다. 테스트가 많이 존재해도 새 필드가 생성→저장→복원까지 유지되는지는 놓칠 수 있다는 구체적 사례다.

## 8. 아직 설계·제안인 범위

`docs/design/server-android.md`는 서버·Android 확장을 명시적으로 **구현 없는 설계**로 구분한다. FastAPI, PostgreSQL, MinIO, Redis, A100/vLLM, Android 동기화는 현재 데스크톱 구현 기능으로 소개하면 안 된다. 문서의 처리량·시간 수치도 실측 성능으로 간주할 수 없다.

PDF 텍스트/픽셀 diff, 변경점 목록, 디렉터리 비교, 주석을 포함한 PDF 내보내기 등도 현 소스에서 구현을 확인하지 못한 로드맵 항목이다. 반면 TOC·야간 모드·최근 파일·요약 내보내기는 후속 개발로 구현되어 있다.

## 9. 권장 개발 순서

1. **저장 신뢰성:** narrative 필드의 저장·복원 및 전체 요약 왕복 검증, 마커 저장 실패 알림을 우선한다.
2. **검증 환경:** duti 탐색을 격리해 단위 테스트를 정상화하고 E2E의 사용자 저장소 격리를 점검한다.
3. **문서 식별·번역 재사용:** 경로 정규화와 기존 캐시 이관 정책, 번역본 재번역 방지를 묶어서 처리한다.
4. **구조·문서 정리:** PDF·요약·메모 상태 제어를 분리하고 README·로드맵을 현재 구현과 일치시킨다.
5. **제품 방향 선택:** 연구 독서 도구라면 이어보기·문서 보관함·주석 활용을, 비교 도구라면 PDF 실제 diff를 우선한다. 서버·Android 확장은 로컬 저장 규칙이 안정된 뒤 진행한다.

현재는 기능이 없는 초기 시제품보다는 실사용 피드백을 여러 차례 반영한 데스크톱 앱에 가깝다. 다음 개발의 핵심은 기능 수 확대보다 **이미 만든 기능의 저장·복원 일관성과 회귀 검증**이다.
