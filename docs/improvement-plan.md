# wcompare 개선 방안 (최종 · 3라운드 비평 반영)

> 대상: `feat/pdf-dual-viewer` · 작성일 2026-08-01
> v1 초안에 대해 3라운드에 걸쳐 8건의 비평을 받아 반영한 최종본입니다. 이 문서는 **v1~v3 없이 단독으로 읽고 착수할 수 있게** 쓰였습니다. 이전 판을 참조하라는 지시("v2와 동일" 등)는 모두 본문에 풀어 넣었습니다.

## 이 문서가 훑은 범위와 제외한 범위

**훑은 범위.** PDF 이중 뷰어 경로(열기·번역·마커·요약·보관 폴더·최근 파일·PDF 기본 앱·크래시), 그리고 이 경로를 떠받치는 저장소·설정·테스트 하네스입니다. 근거는 저장소 코드, 이 사용자의 실제 서재(`/Volumes/EX400U/.local/wcompare`), `~/Library/Application Support/wcompare`, macOS 크래시 리포트, `npm test` 실행 결과입니다.

**제외한 범위.** diff 모드(Monaco·vim·lint·마크다운), 찾기, TOC 드로어, 동기 스크롤, 사전 조회, 프로젝트 저장/복원, URL 다운로드는 **이번 판에서 보지 않았습니다.** "문제가 없다"가 아니라 "확인하지 않았다"입니다. 아래 목록에 이들 기능의 항목이 없는 것을 품질 보증으로 읽으면 안 됩니다.

**기존 로드맵과의 관계.** 저장소에는 이미 `docs/feature-roadmap.md`가 있고 P1 4건(TOC 패널, 야간 모드, PDF 텍스트 diff, 변경점 목록)과 독자 기능(미러 점프 3.2, 읽기 세션 이어보기 3.7 등), 그리고 M1~M4 추천 순서를 담고 있습니다. **이 문서는 그 로드맵을 대체하지 않습니다.** 이 문서는 "지금 코드에 있는 결함과 위생"을 다루고, 로드맵은 "없는 기능을 새로 만드는 일"을 다룹니다. 겹치는 항목은 아래 12번(이어보기 = 로드맵 3.7) 하나뿐이며, 로드맵의 나머지 P1(2-#3 PDF 텍스트 diff, 2-#4 변경점 목록, 3.2 미러 점프)에 대해서는 이번 판이 아무 판단도 하지 않았습니다 — 폐기된 것이 아니라 다루지 않은 것입니다.

## 2. "지금" 항목별 상세

### 1. 마커 저장 실패가 조용하다 `S`

**문제.** `app.js:268`의 `pagehide` 핸들러가 마커 저장 실패를 `.catch(() => {})`로 완전히 삼킵니다. `app.js:260`의 일반 저장 경로도 `console.warn`뿐입니다. 마커는 유일본이라 잃으면 되찾을 길이 없는데, 사용자는 잃었다는 사실조차 알 수 없습니다. 실패는 실제로 일어날 수 있습니다 — 이 사용자의 storageDir은 외장 볼륨으로 이어지는 심링크 체인(`~/.local` → `ex400u/.local` → `/Volumes/EX400U/.local`)이고, 볼륨이 빠지면 `settings.js:66-72`의 `dirFor()`가 `mkdirSync`에서 실패합니다.

**폐기한 처방과 그 이유.** 초안은 이 `.catch`를 `console.warn`으로 바꾸는 것이었습니다. 그러나 `pagehide`는 렌더러가 해체되는 도중이라 DevTools 콘솔이 이미 닫혀 있어 사람에게 닿지 않습니다. 실효 없는 변경입니다. 그 대안으로 검토한 `userData/markers-save-errors.log`도 **같은 결함을 반복합니다** — 사용자가 열지 않는 파일입니다.

**제안 (하나로 확정).** 사용자에게 닿는 채널은 **상태 줄** 하나로 확정하고, 로그 파일은 보조 기록으로 강등합니다.

- **본안 — 다음 창 로드 시 상태 줄 1회.** main이 마커 저장 실패를 모듈 변수에 누적하고(사유 `errno`, 경로, 시각), 다음 창의 렌더러가 준비된 직후 상태 줄에 한 번 띄웁니다.
  - **노출 시점:** 창의 `did-finish-load` 이후 첫 IPC 응답에 실어 보냅니다. 세션 중 새 실패가 생기면 그때 한 번 더.
  - **문구:** `마커 저장에 실패했습니다 (n건) — 보관 폴더를 확인하세요`. 상세 사유는 툴팁에.
  - **중복 억제:** 창당·세션당 1회. 같은 `errno`는 합쳐 건수만 셉니다.
- **보조 — 로그 파일.** `userData/markers-save-errors.log`에 append합니다. 사용자에게 닿는 채널이 아니라 사후 조사용 기록임을 명시합니다.
- 렌더러의 `pagehide` catch 자체는 타이밍상 손댈 수 없어 그대로 두되, 실패 기록은 main이 대신 남깁니다.

**첫 단계.** `markers:save` IPC 핸들러(`ipc.js:266-270`)에서 `markerStore.save`의 예외를 잡아 실패 큐에 넣습니다. 이 큐가 9번(archive/summary 실패 신호)이 재사용할 통로가 됩니다 — **1번이 배선을 만들고 9번이 얹습니다.**

**위험.** 낮음. 저장 동작 자체는 바뀌지 않고 실패 시 기록만 늘어납니다. 상태 줄은 이미 페이지·배율 표시에 쓰이므로 자리 다툼 규칙만 정하면 됩니다.

**검증.** 지금 하네스(`node --test test/*.test.js`, 25개 파일)에는 **electron을 require하는 테스트가 0건**이고 스텁 장치도 없습니다. `ipc.js`는 electron에 묶여 있으므로 단위 테스트가 그대로 붙지 않습니다. 따라서 두 단계로 나눕니다:

1. 실패 큐(누적·중복 억제·건수 집계) 로직을 electron 미의존 모듈로 추출합니다(`src/main/saveFailures.js` 신설 또는 `markerStore.js`에 병설). → 단위 테스트 1건.
2. 쓰기 실패를 강제로 유발(읽기 전용 storageDir)한 뒤 다음 창 상태 줄에 문구가 뜨는지 e2e 1건.

### 2. 경로 정규화를 한 곳으로 통일 `2a: XS · 2b: S`

**문제 (실측).** `~/Library/Application Support/wcompare/recent-files.json`의 10칸을 열어 보면 **4쌍 = 8칸이 같은 파일의 NFC/NFD 두 형태**입니다. NFC로 접으면 distinct 6개입니다. 쌍의 기록 시각차는 **10 / 292 / 318 / 589ms**로, 한 번의 열기 동작에서 두 칸이 만들어졌음을 보여 줍니다. `recentProjects.js:30`의 중복 제거가 `x.path !== abs` 문자열 비교라 정규화 형태가 다르면 통과합니다. 한글 이름에서만 나타나며, 유일한 ASCII 이름(Open-Weights)에는 중복이 없습니다.

**같은 뿌리가 마커·요약에도 있습니다 (이번 판에서 새로 확인).** `allowlist.js`의 `normalize()`는 `fs.realpathSync.native`인데, **realpath는 유니코드 정규화 형태를 바꾸지 않습니다.** 직접 실측했습니다 — NFD 경로를 넣으면 NFD 그대로 나오고 sha1도 달라집니다. 그런데 `markerStore.js:22-27`과 `summaryStore.js:34-39`의 `fileNameFor()`는 `sha1(path.resolve(absPath))`가 파일 이름의 전부이고, `markers:save`/`markers:load`(`ipc.js:266-274`)는 이 `normalize()` 결과를 그대로 키로 씁니다.

> 즉 같은 PDF를 Finder 더블클릭으로 한 번, dialog/DnD로 한 번 열면 **마커 파일이 두 개로 갈리고, 한쪽을 열었을 때 `markers:load`가 `[]`를 돌려줍니다.** 이 문서가 최상위에 둔 "비가역 손해"입니다.

지금 markers/의 실사용 5건은 경로가 전부 NFC라 아직 터지지 않았습니다. 하지만 `recent-files.json`은 **NFD 경로가 실제로 이 앱에 들어오고 있다**는 증거입니다.

**발생원 (미확인).** 초안은 "`main.js`의 `record(f)`(원시 경로)와 `ipc.js:153`의 `record(p)`(realpath)가 서로 다른 형태를 기록한다"고 적었으나, 위 실측대로 realpath는 형태를 바꾸지 않으므로 이 설명은 틀렸습니다. 갈림은 realpath **이전** — Finder의 `open-file` 이벤트와 dialog/DnD가 서로 다른 형태를 전달하는 데서 옵니다. **어느 쪽이 NFD를 주는지는 확인하지 않았습니다(추정).** 그래서 처방을 입구 쪽이 아니라 **키 정규화 한 곳**으로 통일합니다 — 입구가 몇 개든 키가 하나면 갈리지 않습니다. (인용 정정: 해당 줄은 `main.js:52`입니다.)

**제안.**

### 6. PDF 기본 앱: 안내 문구 + 죽은 코드 `S`

**문제.** `defaultApp.js`는 UTI 형태(`com.adobe.pdf`)로 duti를 호출합니다. "등록에 성공(exit 0)해도 실제로 반영되지 않는 경우가 있다"는 것은 사용자가 전달한 실측이며, **저는 재현하지 못했습니다(추정).**

**남는 것 두 가지.**

- **① 죽은 분기 정리.** `ipc.js:252`의 `const self = app.getBundleId?.() || 'com.wooix.wcompare'`에서 `app.getBundleId`는 **Electron에 존재하지 않는 메서드**입니다(Electron 42.4.0 직접 실행: `typeof app.getBundleId = undefined`, `node_modules/electron/electron.d.ts`에 grep 0건). `?.()`는 항상 `undefined`이고 `||` 폴백이 항상 걸려 `'com.wooix.wcompare'`가 나갑니다. `scripts/pack-mac.mjs:13,54`가 패키징본의 `CFBundleIdentifier`를 같은 값으로 굽고 있어 패키징본과도 항상 일치합니다. `?.()` 분기를 제거하고 상수 하나를 공유하거나, 최소한 죽은 분기임을 주석으로 남깁니다.
- **② 안내 문구가 즉시 지워진다.** `app.js:1225-1238`의 `setPdfDefault()`는 `if (res.ok) { await refreshPdfDefault(); return; }`이고, `refreshPdfDefault()`가 1222행에서 `hint.textContent`를 **무조건 재작성**합니다. 따라서 `res.ok && !res.isOurs`(등록은 성공했는데 우리 앱이 기본이 아님)일 때 추가하려는 안내 문장은 `refreshPdfDefault()` 호출 **이후**에 써야 살아남습니다. `refreshPdfDefault(extraHint)` 형태로 통로를 엽니다.

**③ 테스트 심을 함께 넣습니다 (신규).** IPC 핸들러 `system:pdf-default`(`ipc.js:251-259`)는 `getPdfHandler()`·`setPdfHandler(self)`를 **인자 없이** 호출합니다. `defaultApp.js`가 `run`/`env` 주입 seam을 가지고 있어도 IPC 경로에서는 쓰이지 않습니다. 그래서 e2e로 ②를 검증하려 하면 **duti가 깔린 머신에서 사용자의 진짜 LaunchServices 등록을 일으키거나**, duti가 없으면 `res.ok`가 false라 그 경로에 아예 닿지 못합니다. 이것은 자동 재시도 안을 폐기한 바로 그 사유(사용자 시스템을 실제로 바꾸는 부수효과)와 같은 종류입니다.
→ 이미 쓰는 관용구(`WCOMPARE_DICT_FAKE`, `WCOMPARE_TEST_TRASH`, `WCOMPARE_TEST_CONFIRM`)를 따라 **`WCOMPARE_DUTI_FAKE`** 심을 핸들러에 추가합니다. 설정되면 `{ ok:true, handler:'com.other.app' }` 같은 고정 응답을 돌려주어 LaunchServices를 건드리지 않습니다. 이 심을 만드는 비용이 이 항목을 XS가 아니라 **S**로 만듭니다.

**첫 단계.** `WCOMPARE_DUTI_FAKE` 심을 먼저 넣습니다 — 심이 있어야 ②의 검증이 안전하게 성립합니다.

**위험.** 낮음. 죽은 코드 제거와 호출 순서 수정 모두 동작 변경이 없습니다. 테스트 심은 e2e 전용이며 기본 경로에 영향이 없습니다.

**검증.** ① `getBundleId?.()` 분기 제거 후 `npm test` 회귀 없음. ② `WCOMPARE_DUTI_FAKE`로 `ok && !isOurs`를 흉내 낸 뒤 안내 문장이 화면에 **남아 있는지** e2e 1건.

### 8. 요약 저장 load→merge `S`

**문제.** `generateSummary()`(`app.js:356`)는 항상 `parts = { overview:'', sections:'', flow:'' }`(376행)로 시작해 `finally`에서 통째로 저장합니다(405-409행). `summaryStore.save`는 병합하지 않으므로(`summaryStore.js:16-21` 주석이 명시), 세 종류 중 하나만 실패해도 그 kind는 빈 문자열로 저장되어 **디스크에 있던 멀쩡한 캐시가 지워집니다.**

**방아쇠는 LLM 실패만이 아닙니다.** 루프 안의 `if (!alive()) return`(382·393행)은 문서 전환 시 발동하는데, 이 `return`은 `finally`를 지나갑니다. 거기서 "여기까지 만든 것은 그 문서의 캐시로 남긴다"는 주석과 함께 **부분 `parts`가 그대로 저장됩니다.** 요약을 만드는 중에 다른 문서를 열기만 해도 캐시가 잘립니다. 실사용 요약 8건이 이 상태에 노출돼 있습니다.

**제안.** 저장 직전에 `summaryStore.load(dir, absPath)`로 디스크의 현재 parts를 다시 읽어, 이번에 새로 만든 kind만 갈아 끼운 뒤 저장합니다(`load`/`save` 모두 이미 존재). 탭별 "이 탭만 다시" 버튼은 이 수정과 독립된 편의 기능으로 미룹니다.

**참고.** `summaryPanel.js`의 공개 API는 9개입니다: `el` / `setPart` / `setBusy` / `setError` / `setTab`(330-340) / `setTheme` / `getTab` / `hasContent` / `reset`. 원문 마크다운을 돌려주는 getter는 없습니다.

**위험.** 낮음. DOM 변경 없이 저장 로직만 바뀝니다.

**검증.** `summaryStore`에는 이미 단위 테스트가 있고 electron 미의존이므로 load→merge 로직 단위 테스트가 바로 붙습니다. e2e는 "탭별 재생성 버튼"을 전제하면 안 됩니다(그 UI는 없습니다) — 대신 **가짜 agy로 `sections`·`flow`만 실패시킨 뒤 재생성 → 디스크의 `sections`가 보존되는지** 확인합니다.

### 9. 보관 폴더 쓰기 실패 신호(archive/summary) `S`

### 10. 취소·종료 시 번역 산출물 정리 `S`

**"영구 캐시"는 과장이었습니다.** 탈출구가 이미 둘 있습니다 — 삭제 버튼(`pdf:translation:delete`)이 존재 여부만으로 후보를 찾아 지우므로 잘린 파일도 지울 수 있고, ⌥+클릭(`force=true`)이 `ipc.js:306`의 `if (!force && fs.existsSync(output))` 검사를 건너뛰며 이는 버튼 툴팁에 안내돼 있습니다(`app.js:519`). 게다가 잘린 PDF는 pdf.js가 열지 못해 `alert('PDF를 열 수 없습니다: …')`로 **눈에 보이게** 실패합니다.

**남는 것은 위생 하나인데, "한 줄"로 끝나지 않습니다.** `transpaper.js:166-170`의 `cancel()`은 `canceled = true; process.kill(-child.pid, 'SIGTERM')`만 보내고 **즉시 반환**합니다. 자식은 `detached: true`라 앱보다 오래 삽니다. `translationJobs.js`의 `cancel()`도 map에서 즉시 지웁니다. 따라서 **취소 직후 `fs.rmSync(output)`을 부르면** 그 시점엔 지울 파일이 아직 없거나, 지운 뒤에 transpaper의 `doc.save(out, …)`(`transpaper/cli.py:153`)가 파일을 다시 만들어 **잘린 파일이 그대로 남습니다.**

**제안 (정리 시점을 못박습니다).**

- **취소 경로:** 정리는 `job.promise`가 취소로 reject된 뒤 — 즉 자식의 `close` 이벤트 이후에 합니다. 구현 위치는 순수 모듈인 `translationJobs.js`가 아니라 **`ipc.js`의 `pdf:translate:cancel` / 번역 `finally` 쪽**입니다.
- **종료 경로:** `main.js:99`의 `will-quit` → `cancelAll()`은 정리 주체인 앱이 먼저 죽어 더 나쁩니다. 종료 시 정리는 포기하고, **다음 실행 시작 시 고아 정리**(진행 중 표시가 남은 출력 파일을 시작할 때 치움)로 분리합니다.

**전제 확인.** transpaper가 "tmp+rename 없이 한 번에 저장"한다는 전제는 형제 저장소를 직접 열어 확인했습니다 — `cli.py:153: doc.save(out, garbage=4, deflate=True)`, 저장소 전체에 `os.replace`·`tempfile`·`.tmp` 0건. 다만 **실제로 잘린 파일이 생기는 타이밍은 재현하지 않았습니다(추정).**

**검증.** "취소 직후 출력 파일이 존재하지 않는지"는 **위 경합을 그대로 통과시키는 잘못된 단언입니다.** 대신 **자식의 `close` 이벤트가 온 뒤** 출력 파일이 없는지 확인합니다. 가짜 transpaper 스크립트(`WCOMPARE_TRANSPAPER` 심 활용)로 "SIGTERM을 받고도 잠시 뒤 파일을 쓰는" 자식을 만들어 재현합니다.

### 15. 보관함 훑어보기 `M(1단계) ~ L(2단계)`

**갈림은 아직 실제로 일어나지 않았습니다.** 확인된 것은 같은 stem 파일이 두 폴더에 있다는 사실뿐입니다(`2001.08361`, `2203.15556`). 마커·요약이 실제로 두 키로 갈린 사례는 **0건** — `2203.15556`의 마커 9개·요약 1건은 모두 `downloads/` 한쪽에 몰려 있습니다. "잠재적 갈림"입니다. (참고 수치: `documents/` 75개 중 `.ko.pdf` 29개 = 38.7%, 요약 분포는 documents 4 · downloads 3 · 외부 1.)

**규모 (M으로 통일).** 1단계는 초안의 `S`가 아니라 **`M`**입니다. 1단계가 두 사본을 한 줄로 접고 클릭 시 main이 경로 하나를 고르는 구조라면, 마커 9개가 붙은 `downloads/2203.15556.pdf`가 아니라 마커 0개인 `documents/` 사본을 고를 위험이 **1단계 자체에** 있습니다(2단계 배지 정확도만의 문제가 아닙니다). 위험도 "낮음"이 아니라 **"중"**입니다.

- **1단계 (`M`).** 목록 단위를 "파일"이 아니라 "논문(stem)"으로 잡고 `documents/`·`translations/`·`downloads/`를 훑어 같은 stem을 한 줄로 접습니다(배지 없이 원본/번역본 유무만). 렌더러에는 `{id, displayName, badges}`만 내려보내고, 클릭 시에만 main이 실제 경로를 전달합니다(신뢰 경계 유지).
- **2단계 (`L`, 1단계 이후 재검토).** "마커 n개" 배지는 `markers/`·`summaries/` JSON의 `path` 필드를 역색인해 판정하되, 사본과 원본을 같은 논문으로 묶는 매칭 규칙은 이 항목의 범위를 넘습니다.
- **더 싼 대안.** 드로어 대신 `dialog.showOpenDialog({ defaultPath: documentsDir, properties: ['openFile'] })`. 1단계 결과를 보고 채택 여부를 정합니다.

**검증.** 1단계: 가짜 폴더 트리로 stem 그룹핑 단위 테스트(순수 함수라 바로 붙습니다) + "드로어가 열리고 클릭하면 열린다" e2e 1건. 2단계는 매칭 규칙이 정해진 뒤 별도 검증 계획이 필요합니다.

## 4. 보류·하지 않을 것

### 16. 마커 목록과 이동 `보류`

텍스트를 빼고 `{페이지, 색, 저장 시각}`만 남기는 축소판을 검토했으나 **가치가 거의 0입니다.** 마커 레코드 스키마(`projectFile.js:25-31`)에 텍스트가 없고, `savedAt`은 마커별이 아니라 **파일 단위 필드 하나**입니다(`markerStore.js:54`). 실사용 5개 파일을 파싱하면:

```
9개  2026-07-30  2203.15556.pdf        2개  2026-07-29  2203.15556.ko.pdf
1개  2026-07-22  2309.06180v1.pdf      8개  2026-07-22  2309.06180v1.ko.pdf
3개  2026-07-27  2304.15004.pdf
```

즉 목록의 모든 행에 같은 날짜가 찍히고 남는 정보는 페이지 번호와 색뿐입니다. 형광펜을 친 이유는 문장에 있지 페이지 번호에 있지 않고, "페이지로 점프"는 이미 있는 TOC 드로어가 절 제목까지 붙여 더 잘합니다. 텍스트 추출(pdf.js 텍스트 레이어 재조회 + 스키마 버전업)을 감당할 근거가 생기면 재검토합니다.

### 17. 성능 부채 3종 `보류`

재측정해도 동일합니다: `settings.get()` 0.016ms, `dirFor()`의 `mkdirSync` 0.0025ms, `file:readBytes` 2.7ms, `archivePdfIfEnabled`의 `copyFileSync` 4.0ms. "UI가 멎는다"는 근거가 나오지 않았고, 실사용(최대 7MB대 논문 PDF)에서 극단 사례가 없습니다. **이 판단은 14번이 길이 상한을 유지한다는 전제에 의존합니다** — settings.json이 830B이기 때문에 0.016ms입니다.

### 18. `dirtyGuard`의 `prompt()` 교체 `보류`

diff 모드에서 파일을 수정한 뒤 다른 파일을 열 때만 지나는 경로입니다. 이 사용자의 주 용도(PDF 대조 읽기)에는 dirty 상태가 없습니다.

### 19. 오른쪽 pane URL 입력 `보류`

`pdfDualView.js:106`의 `URL_SIDES = ['left']`와 주석("요구사항")이 의도적 비대칭임을 그대로 말하고 있습니다.

### 20. Word PDF 블록 파편화·링크 재정박 잔여 한계 `보류`

원인이 저장소 밖(transpaper)이고, 사용자가 이미 "원본 문제이니 무시"로 판단한 사안입니다. 뒤집을 새 근거를 찾지 못했습니다.

## 5. 마감 절차 — 고친 코드가 사용자에게 도달하는 경로

위 20개 항목은 전부 main 프로세스·렌더러 소스를 고치는데, 검증 수단은 `npm test`(`node --test test/*.test.js`)와 playwright뿐이고 e2e의 진입점은 `src/main/main.js`(각 spec의 `MAIN` 상수)입니다. **사용자가 실제로 여는 것은 패키징된 .app입니다.** `npm run build`만으로는 .app에 반영되지 않습니다 — `npm run package:mac`(= `npm run build && node scripts/pack-mac.mjs`)을 지나야 합니다.

**"지금" 버킷을 끝낸 뒤 반드시 다음을 합니다:**

1. `npm test` → 307/307 초록불 확인.
2. `npx playwright test` 1회 → 이때 4-①(격리)이 붙어 있어야 서재가 오염되지 않습니다.
3. `npm run package:mac` 1회.
4. **실제 .app을 열어 육안 확인 2건** — ① 번역본을 열었을 때 번역 버튼이 비활성인지(3번), ② 한글 이름 PDF를 Finder 더블클릭과 dialog로 각각 연 뒤 최근 파일에 한 칸만 생기는지(2번).
5. 마지막으로 4-②(잔해 정리, 드라이런 → 대조 → 휴지통)를 한 번 실행합니다.

이 절차를 빼면 위 항목을 다 끝내고도 사용자 체감이 그대로일 수 있습니다.
